# ECU6 Gateway/OTA/Security Design

Source requirement document: `C:\Users\JunsangS\Downloads\MPC5748G_Embedded_Training_Requirements_EN.docx`

Project scope: this S32DS project is treated as the ECU6 Gateway + OTA + Security node. The full training requirement document contains all six ECU roles, but this project currently contains ECU6-oriented source, CANoe tests, and Trace32 scripts.

## 1. Role

ECU6 monitors selected primary CAN status messages from ECU1 through ECU5, reports gateway health on `GatewayStatus` CAN ID `0x601`, and provides the transport foundation for OTA request/response CAN IDs `0x650` and `0x651`.

## 3. CAN Interfaces

| CAN ID | Direction | Purpose | Current handling |
| --- | --- | --- | --- |
| `0x101` | ECU1 to ECU6 | BodyStatus | Monitored, checksum/alive/timeout supervised. |
| `0x201` | ECU2 to ECU6 | PowertrainStatus | Monitored, checksum/alive/timeout supervised. |
| `0x301` | ECU3 to ECU6 | SensorStatus | Monitored, checksum/alive/timeout supervised. |
| `0x401` | ECU4 to ECU6 | ClusterStatus | Monitored, checksum/alive/timeout supervised. |
| `0x501` | ECU5 to ECU6 | DiagnosticStatus | Monitored, checksum/alive/timeout supervised. |
| `0x601` | ECU6 to all/CANoe | GatewayStatus | Transmitted every 100 ms by `vCANTask()`. |
| `0x650` | CANoe to ECU6 | OTA_Request | Received by the OTA RX mailbox. |
| `0x651` | ECU6 to CANoe | OTA_Response | Response frame is generated by `OTA_HandleRequestMessage()`. |

## 4. GatewayStatus Payload

| Byte | Signal | Notes |
| --- | --- | --- |
| 0 | GatewayState | `0=INIT`, `1=NORMAL`, `2=DEGRADED`. |
| 1 | OTA/security/error flags | Bits 0..2 OTA state, bit 3 SecurityUnlocked, bit 4 SecurityLocked, bit 5 AliveError, bit 6 ChecksumError. |
| 2 | BlockedMsgCnt | Saturating counter for unknown IDs and checksum failures. |
| 3 | SecurityErrorCounter | Increments on failed seed/key/AuthByte security attempts. |
| 4 | ActiveSWVersion | Starts at version `1`; increments only after verified OTA activation. |
| 5 | GatewayRxMask | Bit mask showing which monitored ECU messages have been received. |
| 6 | AliveCounter | 4-bit ECU6 alive counter, wraps `0..15`. |
| 7 | Checksum | XOR checksum over CAN ID LSB and bytes 0..6. |

## 5. State Machines

Gateway state is implemented in `COM_UpdateGatewayState()`:

| State | Entry condition |
| --- | --- |
| INIT | Not all monitored ECU messages have been seen yet. |
| NORMAL | All monitored ECU messages have been seen and no alive/checksum faults are active. |
| DEGRADED | Any timeout, alive freeze, or checksum fault is active. |

OTA state handling is implemented in `OTA_ApplyCommandState()`:

| State | Entry condition |
| --- | --- |
| IDLE | Reset/default state after `COM_GatewayInit()`. |
| START | `OTA_CMD_START` is accepted. |
| RECEIVING | `OTA_CMD_DATA` is accepted after START or RECEIVING and payload bytes are stored in the OTA buffer. |
| VERIFYING | `OTA_CMD_END` is accepted after START or RECEIVING. |
| READY_TO_ACTIVATE | The first GatewayStatus publish after a successful OTA payload checksum verification. |
| SUCCESS | `OTA_CMD_ACTIVATE` is accepted from READY_TO_ACTIVATE after checksum verification, and `ActiveSWVersion` is advanced. |
| FAILED | `OTA_CMD_ABORT` or an invalid command sequence is received. |

Security access is implemented with `REQUEST_SEED` (`0x10`) and `SEND_KEY` (`0x11`). The key is calculated as `seed XOR 0xA5`; a successful key unlocks OTA and clears the security failure streak. `OTA_CMD_START` is rejected while locked. Three consecutive wrong key/AuthByte attempts activate security lockout for 3000 ms. During lockout, all known OTA commands are rejected with NACK detail `0x23`; after the timeout, `REQUEST_SEED` can be accepted again but OTA remains locked until a valid key is sent.

OTA data buffering and authentication are implemented for `OTA_DATA` (`0x02`). Byte 2 carries the payload length (`0..4`), byte 3 carries `AuthByte`, and bytes 4 through 7 carry payload data. The expected AuthByte is `seed XOR sequence XOR payloadLength XOR 0xC3`, where `seed` is the last issued security seed. A wrong AuthByte is rejected with detail `0x18`, increments `SecurityErrorCounter`, and moves OTA state to FAILED. ECU6 stores accepted data in a 256-byte bounded buffer. A payload length greater than 4 is rejected with detail `0x15`; a transfer that would exceed 256 bytes is rejected with detail `0x16` and moves OTA state to FAILED.

OTA checksum verification is implemented on `OTA_END` (`0x03`). Byte 2 carries the expected payload checksum. ECU6 calculates an 8-bit XOR checksum over the stored OTA payload bytes. A correct checksum enters VERIFYING and then READY_TO_ACTIVATE (`VERIFY_OK` in the requirement wording); a wrong checksum is rejected with detail `0x17` and moves OTA state to FAILED without changing `ActiveSWVersion`.

Active software version handling is implemented on verified activation. `ActiveSWVersion` starts at `1`; `OTA_CMD_ACTIVATE` advances it only when the OTA state is READY_TO_ACTIVATE and the payload checksum verification result is OK. READY_TO_ACTIVATE alone does not change the version. The version advances by one successful activation and wraps from `0xFF` to `0x01`; invalid activation attempts do not advance it.

## 6. Error Handling and Recovery

| Fault | Detection | Current behavior |
| --- | --- | --- |
| Unknown CAN ID | `COM_FindRxMonitor()` returns no monitor | Increments `BlockedMsgCnt` and logs throttled warning. |
| Checksum mismatch | Received byte 7 differs from calculated checksum | Sets checksum error, increments `BlockedMsgCnt`, reports in GatewayStatus. |
| Alive freeze | Alive counter repeats for configured limit | Sets alive error and reports in GatewayStatus. |
| Timeout | Monitored ECU message missing for `COM_RX_TIMEOUT_MS` | Sets timeout/alive error and logs the event. |
| Security lockout | Three wrong key/AuthByte attempts before a successful unlock | Rejects known OTA commands with detail `0x23` for 3000 ms, keeps `SecurityLocked=1`, and clears lockout after timeout. |
| Recovery | Valid messages resume | Clears timeout/alive faults; checksum clears after valid recovery count. |
